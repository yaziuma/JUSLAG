# JUSLAG 統合実施計画（2026-09-18）

## 位置づけと結論

この文書を当面の作業順序の基準とする。既存の[研究引き継ぎメモ](reports/continuation_notes_20260916.md)と[提供されたTurso化計画書](JUSLAG_Turso化計画書_2026-09-18.md)を統合した。元の計画書は構想・候補スキーマの記録として維持し、本書が実施順・採用条件を定める。実装は未着手であり、以下のTurso機能やSDK採用はPoCで確定する。

**二本立てで進める。** Aは戦略の実行可能性検証、Bは研究結果の保存・閲覧基盤整備。BはAを待たずに小規模PoCを進めてよいが、Bの完成をもって実売買へ進んではならない。現行メタ版の当日寄りgap判定後に同じ寄り値で約定する前提は未検証であり、発注候補の禁止を維持する。

| 優先 | トラック | 次の成果物 | 完了ゲート |
| --- | --- | --- | --- |
| P0 | A: 時刻・執行 | US/JPの情報利用可能時刻の表、寄りgap後約定のデータ要件 | 先読みがない評価仕様と、必要データの取得可否が明確 |
| P0 | B: 保存PoC | 既存ファイルを残すTurso二重書きPoC | 再実行・失敗復旧・照合が自動テスト可能 |
| P1 | A: 代替戦略 | 低回転案の資金制約付きウォークフォワード | 借株・税・実勢コストを入れて採否を判断可能 |
| P1 | B: 閲覧PoC | 認証された過去30日の検索・比較画面 | 秘密を配布せず、鮮度と欠損を表示できる |
| P2 | B: 切替判断 | Git生成物縮退・ブラウザ内DB採否・価格キャッシュ評価 | 旧Pagesへの復旧手順と運用実績が揃う |

## 現在地と変更しない境界

- 日次バッチは`daily_research.py`がレポートJSON・戦略履歴JSONL・signals.csv・regime.json・監査抽出を保存し、`daily_research.sh`がLLM/フォールバック要約を`history.jsonl`へ追記してSlack通知する。Actionsは`data/`をGitへcommit/pushし、Pages用HTMLを生成してStatiCryptで保護する。保存時点が二つあるため、要約を含む確定スナップショットはシェル処理後に作る。
- 価格入力のSQLiteキャッシュ`~/.juslag/prices.db`と`actions/cache`は維持する。Tursoを価格の唯一の原本にしない。raw監査抽出も初期段階では維持する。
- 論文準拠PCAのローカル再現は済んだ。現行メタ版の見かけの税前プラスは寄りgap同値約定の未検証前提に依存する。gapを使わない版は税前マイナスであり、Turso化によって戦略の有効性が上がるわけではない。数値と条件は[再計算](reports/backtest_recheck_20260917.md)・[gap除外比較](reports/preopen_gap_ablation_20260917.md)を参照。
- Pagesの簡易認証は既存閲覧経路だけを保護する。将来のブラウザDB接続の資格情報を守る認証として流用しない。

## A. 戦略・執行可能性

### A1. 情報時刻の監査（最初に実施）

各評価日について、US終値の確定・配信、JP寄り前の判断締切、JP寄りgap確定、注文送信、実約定の順序を定義する。米国のみ開場した日と日本のみ開場した日も含め、履歴シグナルがその時点で知り得た価格だけを使うか検証する。タイムゾーンと祝日、データ提供の遅延、再取得による過去値改訂を記録する。結果は日別の情報集合監査と先読みテストとして残す。

### A2. 現行メタ版の約定検証

寄りgapを観測した後に取れる価格を、板・ティック・少なくとも寄り後の時系列データまたは実約定記録で評価する。注文時刻、買/売建可否、約定率、数量、スプレッド、スリッページ、HYPER料等を収集する。日次OHLCだけで同じ寄り値約定を認めない。必要データを得られない場合は現行ルールを研究専用のまま据え置く。

### A3. 代替案の独立評価

低回転・持越し案は既存の日中ルールとは別戦略として実装する。固定資本、同時建玉、売建可否、在庫、実測または保守的なコスト、税、ウォークフォワード分割を組み込む。既存の保有期間イベントスタディは重複保有窓を持つため、採用判定には使わない。採否基準は実装前に固定し、アウト・オブ・サンプルの税前/税後、最大DD、約定不能日、感度を報告する。

**AのGo/No-Go:** A1/A2が未完ならライブ発注はNo-Go。A3も評価条件を満たさなければ「研究結果の閲覧基盤」としてのみ運用する。自動発注・資金投入は本計画の範囲外。

## B. Turso保存・閲覧基盤

### B0. 製品・契約・認証PoC

1. Turso CloudのDBエンジン種別、Python書き込みSDK、同期SDK、利用上限・費用、バックアップ/復元、リージョンを現行公式ドキュメントと小さな実験で確定する。旧libSQL Embedded Replicasと新Turso Syncを混同しない。SQLite互換性も必要なSQL/JSON関数・トランザクションで確認する。
2. ローカル同期サーバーで「Pythonから書く、別クライアントで読む、切断後に復帰する」を試す。Cloudはその後に最小データで試す。GitHub Actions Secretに書込資格情報を置き、ログ・成果物・DB行へ漏らさない。
3. Viewerの公開範囲を先に確定する。非公開データの場合、静的PagesのJavaScriptへ固定DB tokenを埋め込まない。認証付き読み取りAPI、短命かつ適切に限定した資格情報、または認証済み静的スナップショットのいずれかを比較し、脅威モデルと運用負担で選ぶ。read-only tokenでも漏えいすれば全読取可能範囲が露出する。
4. Cloud読取・同期を増やす設計では、[Turso利用量レビューskill](../skills/juslag-turso-usage/SKILL.md)に沿ってクエリ計画、呼出頻度、キャッシュ、実測使用量、警告と縮退手順を確認する。記事の無料枠数値やNext.js対策を固定要件にはしない。

**B0ゲート:** Cloudを使わないローカルPoC、Secret非露出検査、読み取り認証方針、費用上限の確認。未達ならCloud/Viewer開発へ進まない。

### B1. 出力の二重書き

- 既存ファイルを正本として維持し、日次処理が完全に終わった後に独立したpublisherからTursoへ転送する。バッチの計算結果とSlack通知はTurso障害で失わない。失敗時は非ゼロの同期状態と再送キュー/再実行手順を残し、失敗を黙殺しない。
- 初期スキーマは`runs(run_id, report_date, source_commit, settings_hash, input_hash, output_hash, status, created_at_utc)`、`report_versions(run_id, report_json, generated_at_utc)`、`summaries(run_id, summary, llm_status)`、`signals(run_id, ticker, payload_json)`、`regimes(run_id, payload_json)`を基本とする。実際のカラムはUIの検索要件が確定してから絞る。全表を同一`run_id`で関連付け、1回の公開単位をトランザクションとして扱う。
- 元計画の`report_date PRIMARY KEY`だけでは同日再実行が過去結果を消す。日付ごとの`latest_published_run_id`を別に持ち、過去runは不変で保持する。`run_id`はGitHub run/attemptと対象日から決め、ローカル再実行には別IDを割り当てる。`source_commit`は実行時のコードSHAとし、後から生じる日次データcommitのSHAと区別する。hash対象、正規化方式、欠損値の扱いを仕様化する。
- 既存`strategy_history.jsonl`と`history.jsonl`は同日再実行で追記される。二重書きでは既存の重複をそのまま最新扱いせず、`run_id`単位で照合し、最新選択規則を明示する。要約失敗時のフォールバックも`llm_status`付きで保存する。
- `JUSLAG_WRITE_TURSO`を既定OFFで導入し、資格情報がある時だけ有効化する。既存の`data/` commit、Pages生成、Slack通知は初期期間そのまま維持する。

**B1ゲート:** 単体/統合テストで再送・同日再実行・部分失敗・ロールバックを確認し、同一入力・設定・コードのファイル出力とDB行を10回連続で照合する。hash不一致は公開不可とし、差分を可視化する。

### B2. 認証付き閲覧PoC

最新日・過去30日・シグナル/レジームの検索と2日比較を最小画面で作る。旧Pagesは残す。表示には`report_date`、`generated_at_utc`、最終同期時刻、`run_id`、欠損/遅延、研究専用・発注不可の状態を示す。古いローカルDBを当日最新と誤表示しない。価格キャッシュや秘密情報はブラウザへ送らない。

ブラウザ内Turso WASM+OPFSは**B2の必須前提にしない**。GitHub Pagesで必要なCOOP/COEP等をどう満たすか、対象ブラウザでのOPFS永続性・複数タブ・初回同期量・オフライン再読込・資格情報の保護を実機PoCで検証する。成立しなければ認証付きAPIからの読み取りと、ブラウザ側の通常キャッシュで十分とする。

**B2ゲート:** 権限のない利用者がDBを読めず、画面と旧Pagesの主要値が一致し、古いデータは明瞭に識別できる。PC/スマートフォンで閲覧・再読込・障害時動作を確認する。

### B3. 切替とB4. 価格キャッシュ評価

B1/B2が安定してから、日次生成物のGit commit削減と旧Pages縮退を別々に判断する。監査用raw、コードSHA、設定、入力・出力hash、GitHub Run URLの保持先と復元手順が揃うまでGit履歴を削らない。`JUSLAG_READ_TURSO`をOFFにした時の旧閲覧経路を一定期間維持する。

最後に`PriceCache`を現行SQLite+actions/cacheとTurso Sync/Cloudで同一期間・同一価格モードを使って比較する。価格修復、分割調整、欠損、取得停止時の挙動を含む結果一致、処理時間、同期量、費用、復旧時間を測る。優位性がなければ移行しない。
