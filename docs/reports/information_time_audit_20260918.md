# 情報時刻の一次監査（2026-09-18）

## 判定

**現行メタ戦略は実売買No-Goを維持する。** シグナル日と次の日本営業日の対応はコード上で確認できたが、メタ判定・銘柄除外に執行日の寄りgapを使いながら、損益は同じ寄り値から計算する。日次OHLCでは、そのgapを知った後に同じ寄り値で約定できることを証明できない。これはコスト仮定を調整するだけでは解消しない。

## コード上の情報時系列

| 段階 | 現行経路 | 情報の利用可能時点 / 残る確認 |
| --- | --- | --- |
| JP終値 | `compute_returns()`でJP前日比を作る | JP取引終了後。データ配信・修正履歴は未記録 |
| US終値 | 同関数でUS前日比を作る | 同一カレンダー日付のJP終値より後。US終値の実際の取得時刻は未記録 |
| シグナル | `build_joint_cc()`のUS/JP共通日を学習窓とし、`generate_signals()`は当日US前日比を利用 | US終値確定後。最新US-only日だけ別経路で追加される |
| 執行日 | シグナル日より後の最初のJP行へ`jp_oc`とgapを対応付ける | `portfolio._next_jp_session_values()`は日付で対応。時刻・実約定は扱わない |
| メタ判定 | `build_portfolio_with_strategy_rule()`が次JP日のgapを`StrategyContext`へ渡す | 寄り値の観測後でないと確定しない |
| 損益 | 同じ次JP日の`close/open - 1`を使用 | 寄り値約定を前提とするため、上段の判定時点と両立未証明 |

日次経路も`run_daily_signal_service()`で執行対象日のgapを選び、ルール判定と銘柄除外に使う。対象日の寄り値がまだない場合、過去日のgapでは代用せず欠損となる。Actionsの定時実行はUTC前日23:00、JST 08:00を意図する。この時刻では通常、当日JP寄りgapは未確定であり、同ルールによる最終的な発注判断は作れない。手動再実行では実際の実行時刻と対象日を分けて記録する必要がある。

## A1で未検証の項目

1. US終値・JP終値の配信時刻、取得完了時刻、再取得による過去値改訂。日付だけの価格キャッシュでは時点再現ができない。
2. US-only/JP-only/両市場休場日に、各シグナルが判断締切時点で取得済みの行だけを使うこと。最新日と履歴でUS-only処理が異なるため、日別の情報集合テストが必要。
3. 寄りgapを観測できる最初の時刻、注文送信・受付・約定時刻、実際の売建可能数量と価格。これはA2の板・ティックまたは実約定記録が必要。
4. `regime_df`とpriorの各日について、学習対象の最終日がその判断時点以前であることを自動検査する。

## 日付順序の自動検査（一次）

`scripts/reports/audit_information_time.py`をローカルraw価格キャッシュに対して実行した。既定の評価期間は2022-01-01以上、2026-09-19未満、pretrain終了日は2021-12-31、学習窓は60共通日。1179のUS市場日付を列挙し、うち72日はUS-only市場日付だった。日付順序の違反は0件。CSVは`/tmp/juslag_information_time_audit.csv`へ出力した。再現: `PYTHONPATH=src .venv/bin/python scripts/reports/audit_information_time.py`。

この検査は各市場で少なくとも1銘柄のraw終値がある日を用いる**暦レベルの一次監査**であり、厳密な学習パネル・全銘柄の利用可能性・実際のシグナル生成日を再現しない。US-only日は履歴シグナルではなく、最新日経路の候補日として記録した。`date_order=ok`でも価格配信時刻は未検証、gap観測後に同値寄り約定できるという仮定も未検証である。

同日の追加監査で、CSVに予定判断締切（執行日08:00 JST）、gapの最早観測時点（寄り以降）、現行損益の想定約定時点（寄り）、`audit_result`を追加した。実入力パネルを使った最終集計では1105行が`blocked_gap_same_open_fill`、74行が`not_historical_signal`、日付順序違反は0行。これは1105件の実約定失敗を意味せず、**現行の日次OHLCモデルだけではその約定前提を正当化できない**という仕様上のブロックである。時刻欄は市場日付と定時実行予定から導いたモデル上の時点であり、価格配信・注文・実約定の実測時刻ではない。

続く改修では、raw価格から`compute_returns()`と`build_joint_cc(..., fill_policy="strict")`を再実行し、実際に学習窓へ残る共通行を監査に使用した。1179のUS日付のうち、履歴シグナルの入力パネルにない日付は74件（従来の市場暦ベースではUS-only 72件）。この74件には休場日だけでなく、共通日の欠損除外も含む。対象日をすべて実際のシグナル生成日と呼ぶのは誤りで、CSVの`signal_path=historical_joint_row`のみが履歴生成候補である。なお価格キャッシュに配信・取得時刻はなく、同日の改訂履歴もないため、時点再現は依然として未完である。

NYSE/JPXカレンダーの市場終了時刻もJSTへ変換してCSVへ追加した。1179行すべてで市場終了予定時刻は次JP営業日08:00より前だった（`close_time_unverified=0`）。これは取引所で終値が確定する時刻の検査であり、Yahoo価格をその時刻までに取得できた証明ではない。休場・臨時休場はライブラリ内カレンダーに依存するため、将来の祝日変更は更新・再検証が必要。

追加で`PriceCache`が価格を初めて保存した時刻と改訂時刻を`price_observations`へ追記するようにした。同値の再取得は記録しない。監査は全US/JP対象銘柄の最新入力について、最終観測時刻が次JP日08:00以前かを検査する。ただし既存価格には過去の観測時刻がなく、2026-09-18の再実行では`latest_inputs_observed_before_deadline=0`、各行は`not_recorded`。0件は遅延の証拠ではなく、記録欠落の意味。事前学習窓の全セルや過去の価格版までは検証していない。

## 保存済み日次レポートの時刻監査

`scripts/reports/audit_daily_report_timing.py`で、保存済み52件の`generated_at_utc`と対象JPX日の寄り時刻を突き合わせた。30件は寄り前に生成、12件は対象日の寄り後、10件は対象日より後に生成されていた。寄り前30件すべてに`strategy_context.open_gap`が記録され、そのうち20件は`tradeable=true`だった。一方、この30件に対応する同時保存のraw価格CSVには、対象日のJP価格行が0件だった。少なくとも保存された根拠データから当日gapを再現できず、これらを寄り前に執行可能だった判断として扱えない。旧コードのどの経路でgapが入ったかは未特定であり、記録された`tradeable`は実際の発注・約定を証明しない。

現在のサービスは対象日以外のgapを代用しないうえ、JPXの対象日寄り前（寄り時刻ちょうどを含む）には、データ供給元が値を返してもgapを判定へ渡さない。寄り後にgapを使用する場合も、同じ寄り値での約定は依然として未証明である。

このため、現行の日次サービスでは対象日の寄り以降に同じ寄り値での執行を前提とする判断を`assumed_open_fill_expired`で売買不可とする。`--date`による対象日と実実行日が異なる遡及計算は`retrospective_run`で売買不可とする。新規レポートには`run_provenance`として実開始時刻UTC、分析上のas-of JST、対象日、run種別、US終値/JP終値/JP始値の入力パネルSHA-256を保存する。履歴行の`recorded_at`も実実行時刻とし、UTC版を追加した。SHA-256は入力版の照合用であり、その版が当時実際に取得可能だったことの証拠ではない。旧レポートにはこれらのメタデータがない。
