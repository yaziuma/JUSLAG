# Turso B0 PoC記録（2026-09-18）

## 実測した範囲

- 実施: Codex、2026-09-18。Linux x86_64、`tursodb 0.7.2`、`pyturso 0.7.2`。依存物とDBは`/tmp`に置き、JUSLAG本番依存・Cloudの既存DBは変更していない。
- `tursodb /tmp/juslag-b0-server.db --sync-server 127.0.0.1:18080`に対し、`scripts/ops/turso_sync_poc.py`を実行。別ファイルの2クライアントで、Python書込→push→pull→読取、push前の分離、パラメータ化されたJSON文字列、rollback後の非反映を確認。スクリプトはPASS。
- 既存Cloud資格情報によるHTTP読取/トランザクション内書込/rollbackは別途確認済み。ただしCloud DBエンジン種別や新Syncとの互換性は未判定。
- 続けてサーバーを停止した状態でローカルに書き込み、pushがネットワークエラーで失敗することを確認。同一DBファイルでサーバーを再起動後、再送と新規クライアントの初回bootstrapで3行を読めた。PoCスクリプトの`--server-bin`モードで再現可能。
- サーバーログの`no such table: turso_sync_last_change_id`は再起動PoCでも再現。データ照合は通ったが、この内部エラーの発生箇所・長期運用への影響は未判定。バージョン更新または上流issue照合後、再試験する。
- 追加切り分け: 空DBへのクライアント接続だけでは警告なし。新しいDBで初回の`CREATE TABLE`をpushすると警告が出るが、pushは成功し、サーバーDBにはアプリ用テーブルと`client_id/pull_gen/change_id`を持つ`turso_sync_last_change_id`内部テーブルが残る。したがってアプリ用テーブルが空だからという説明は成り立たない。内部テーブル初期化時の一過性エラーという仮説はあるが、原因確定にはソース/上流確認が必要。
- `tursodb 0.8.0-pre.11`サーバーと`pyturso 0.7.2`でも同じPoCの全照合が通り、同じ警告が再現。0.7.2だけの問題ではない。プレリリースを採用したわけではない。[公式リリース](https://github.com/tursodatabase/turso/releases/tag/v0.8.0-pre.11)。
- `turso db show juslagdb`は`Type: SQLite`、`Locations: aws-ap-northeast-1`を報告。既存の資格情報を表示せず、`pyturso 0.7.2`で新しい一時ローカルDBからCloudへ`pull()`したところ成功し、変更ありを返した。この先行の読取PoCはCloudのアプリデータを変更していない。
- 追加実測（2026-09-18）: `scripts/ops/turso_cloud_sync_probe.py`を`pyturso 0.7.2`と既存`libsql://` URL/ローカル書込トークンで実行。ランダム名の一時テーブル作成・1行挿入を`push()`し、別ローカルDBの`pull()`から行を確認。その後`DROP TABLE`を`push()`し、第三のローカルDBの`pull()`でテーブル不存在を確認。2回実行して両回成功。永続アプリテーブルは作っていない。通信不可のsandbox内試行は`DatabaseError`で失敗し、Cloudへの到達・書込はしていない。
- 実契約確認（2026-09-18）: Turso Platform APIの組織GETとsubscription GETをCLIのプラットフォーム認証で読み取り専用実行。組織`yuichi-ide`は`plan_id=starter`、`overages=false`、`blocked_reads=false`、`blocked_writes=false`。subscriptionも`plan=starter`、`overages=false`、月次。資格情報の値は出力・保存していない。[組織API](https://docs.turso.tech/api-reference/organizations/retrieve)、[契約API](https://docs.turso.tech/api-reference/organizations/subscription)。
- 割当量と使用量（2026-09-18）: 同APIの[plans GET](https://docs.turso.tech/api-reference/organizations/plans)から現`starter`を抽出し、料金0、月間読取5億行・書込1000万行・Sync 3 GB、保存5 GB、DB 100を確認。`turso db inspect juslagdb`の実測表示は使用容量12 kB、読取41行、書込21行、Embedded syncs 90 kB。CLI表示の集計期間は明示されていないため、月次請求使用量と同一と断定しない。
- エクスポート/ローカル復元（2026-09-18）: `umask 077; turso db export juslagdb --output-file /tmp/juslag-b0-export-20260918.db`を実行。DB本体と`-wal`は両方600。WAL込みのSQLite `PRAGMA integrity_check`は`ok`。SQLite backup APIで`/tmp/juslag-b0-restored-20260918.db`へ復元し、`integrity_check=ok`とスキーマ一致を確認。これは**ローカル復元のみ**で、別のTurso Cloud DBへのインポート、PITR、障害時の復旧時間は未検証。[Turso CLI export](https://docs.turso.tech/cli/db/export)。

## 採用候補と保留事項

- Pythonの新Sync候補は`pyturso`。旧libSQL Embedded Replicasとは異なり、明示的な`push()`/`pull()`を使う。同期済みローカルDBのWALは`checkpoint()`と`stats()`で管理する。[公式Python接続](https://docs.turso.tech/connect/python)、[Sync利用法](https://docs.turso.tech/sync/usage)、[ローカル同期サーバー](https://docs.turso.tech/sync/local-sync-server)。
- B1のActionsは短時間の単一writerなので、ローカル同期DBを恒久保持するよりCloudへの直接書込も比較候補。現状のCloud疎通だけでは両方式の再送・障害復旧・費用は比較できていない。
- Viewerは非公開データを扱うため、静的PagesのJavaScriptへ固定トークンを埋め込まない。第一候補は既存の暗号化静的スナップショットを維持し、DB検索が必要になった時だけ認証付き読取APIを検討する。短命トークンでもブラウザへ渡せば読取範囲が露出する。
- [公式料金表](https://turso.tech/pricing)は2026-09-18確認時、Freeを$0/月、5GB保存、月5億行読取、月1000万行書込、月3GB同期と表示。実契約の`starter`割当量はAPIで確認済み。使用量の継続監視、アラート/停止条件は未設定。超過課金無効でも、上限到達時の書込停止や日次処理への影響を検証する必要がある。
- B0ゲート未達: Cloudの最小Sync書込、実契約/割当量/DB単位使用量、エクスポートとローカル復元は確認した。同時writer競合・失敗時の再送はCloudで未検証。内部テーブル警告の原因、Secret非露出検査、使用量アラート、Cloudへの復元/PITRも未確認。B1の二重書きはまだ開始しない。

## 再現

`tursodb`と`pyturso`を0.7.2で用意してローカルサーバーを起動し、別端末から次を実行する。PoCは一時DBだけを使い、資格情報を読まない。

```bash
python scripts/ops/turso_sync_poc.py --url http://127.0.0.1:18080
```

切断・復帰も含めて自動実行する場合は、別プロセスのサーバーを立てずに以下を実行する。`--server-bin`にはローカルにインストールした`tursodb`のパスを渡す。

```bash
python scripts/ops/turso_sync_poc.py --server-bin /path/to/tursodb
```

Cloud試験は書込トークンを環境変数から読み、ランダム名の一時テーブルを作成・削除する。通信・削除に失敗した場合、標準出力に出るテーブル名で残存確認が必要。トークンを出力しない。

```bash
set -a; source .env.turso; set +a
python scripts/ops/turso_cloud_sync_probe.py
```
